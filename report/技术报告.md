# 课径 · 可核算的培养方案问答

## 一、作品概述

### 1.1 背景与问题

高校培养方案是一份"表格 + 条款"的复合文档：学分结构表规定各模块最低学分，课程设置表登记课程代码、学分、模块与开课学期，先修要求表用自然语言写"数据结构与算法或计算机组成原理之一""已完成专业核心课不少于 40 学分，且专业实习考核合格"这类条件。学生最常问的两个问题——「我还差多少学分毕业」「这门课我现在能不能选」——答案不在任何单张表里，必须跨表做**带条件的算术与图遍历**。

现有处理方式及其问题如下：

| 做法 | 主要问题 |
| --- | --- |
| 学生自己翻 PDF 逐条对照 | 跨页表格易看漏；先修条件里的"或/且/学分门槛"容易误判 |
| 通用大模型问答（含 RAG） | 会算错：模型把 160−68 算成 100 并非罕见；且无法给出"第 14 页第 3 行"级别的依据 |
| 教务人工核对 | 成本高、口径不一、无法 7×24 响应 |

这类问题需要同时完成条款定位、规则计算和结果核对。

### 1.2 目标与作品形态

把培养方案的表格与条款解析成**带先修关系的结构化课程知识图**，用自研混合检索定位条款、用**确定性代码**完成学分与先修核算，最终给出"结论 + 必要说明 + 逐条可核对的引用"。学生的已修课程以匿名档案标识持久保存；后续对话可在同一档案上继续核算。

作品由三部分组成，全部位于 Dify **应用层**：

1. **Dify Chatflow 对话应用**（DSL 交付，可直接导入）：意图识别 → 检索 → 调用核算/档案服务 → 按问题类型组织回答；
2. **自研外部知识服务 `campus-kb`**（FastAPI，Docker 化）：实现 Dify 外部知识库契约，并提供学分核算、先修判定、课程档案与修读规划接口；
3. **开源交付物**：服务源码、工作流 DSL 生成脚本、部署脚本、评测集与文档（Apache-2.0）。

### 1.3 技术特点

| 技术特点 | 一句话说明 |
| --- | --- |
| **核算与生成分离** | 数字全部由确定性代码算出（规则 R1–R5），检索只负责"找依据"，模型不参与算术 |
| **表格级结构化** | 解析器保留页码与表行号，引用可精确到"第 14 页第 3 行"，而非只给文档名 |
| **混合检索 + 意图加权** | BM25Plus 与向量通道融合，再按问题类型（先修/学分/学期/模块）加权；实测 Recall@1 由 0.833 提升到 1.000 |
| **零源码修改的深度集成** | 只用官方三种机制（compose 覆盖文件、`.env` 变量、控制台 API）把自研服务接进 Dify，未改一行 `langgenius/dify` 源码 |
| **可持续课程档案** | 用用户自行设置的档案标识绑定已修课程；跨对话读取、追加、查看与清空均由服务端管理 |
| **按风险分层的回复** | 学分与先修结论由规则服务直出；千问只用于意图识别和非关键事实的语言组织，避免模型改写计算结论 |

## 二、需求分析与总体方案

### 2.1 用户与场景

- **主要用户**：本科生（自查学分缺口与选课资格）。
- **次要用户**：教务老师、辅导员（批量答疑口径统一）。
- **MVP 范围**：1 个专业、约 200 份文档（1 份培养方案 + N 份教学大纲）、3 类问题主链路。

三类问题与处理方式：

| 问题类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 核算类·学分 | 「我修完这些还差多少学分？」 | 调 `/audit`：分模块核算，超额不冲抵 |
| 核算类·先修 | 「汽车电子控制我现在能选吗？」 | 调 `/prereq`：表达式树求值，直出“可以选/暂不能选” |
| 档案与规划类 | 「查看我的档案」「给我修读规划」 | 调 `/profile-summary`、`/study-plan`：读取持久化档案并列出当前可修课程 |
| 条款类 | 「转专业后学分怎么认定？」 | 检索原文条款并标注页码/行号 |

### 2.2 非功能需求

| 需求 | 指标 | 达成情况 |
| --- | --- | --- |
| 可解释 | 每个数字可追溯到规则编号与源表行 | ✅ 摘要内嵌规则脚注与引用清单 |
| 可复核 | 第三方按文档页码能核对到原文 | ✅ 引用含页码 + 表行号 |
| 可离线自测 | 不依赖 Dify 界面即可验证核心逻辑 | ✅ 149 项 pytest 全绿 |
| 部署轻量 | 单机 2C4G 可跑 | ✅ 本机 16 GB 内存实测全栈运行 |
| 合规 | 不修改 Dify 源码、不引入 AGPL | ✅ 见第七章 |

## 三、AI 技术与开源及第三方资源选择

### 3.1 AI 在系统中的作用

| 环节 | 是否用模型 | 说明 |
| --- | --- | --- |
| 结构化抽取（表格 → 课程/模块/先修表达式） | 否 | 规则 + 表头别名词典，字段准确率可测（≥95%） |
| 检索排序 | 混合：词法 + 向量 | BM25Plus 与稠密向量融合（weighted / RRF），再叠加意图加权 |
| 意图识别与课程提取 | 千问 + 规则校验 | 千问识别意图、提取用户明确表述的已修课程代码；代码节点保守校验并提供关键词回退 |
| 核算 | **否（关键决策）** | 全部确定性代码，杜绝模型算术错误 |
| 答案组织 | 分层处理 | 先修结论由服务端短答案直出；学分与条款问答可由千问在受限上下文中组织表达 |

千问模型用于意图识别、课程代码提取和受限上下文下的语言组织，输出须经规则校验。学分计算、档案状态与选课资格由确定性代码处理，避免模型改变计算结果。

## 四、设计与实现过程

### 4.1 功能流程

**链路 A（核算·学分）**：用户输入档案标识及已修课程代码 → Chatflow 检索相关条款 → 意图识别与代码校验 → `/audit` 合并档案后按模块核算缺口 → 千问仅基于系统结果组织回答 → 回答附条款清单。

**链路 B（核算·先修）**：问题含"先修/能不能选" → 分流到 `/prereq` → 服务端合并档案、解析目标课程、执行表达式树求值 → 以 `brief` 格式直出“可以选。”或“暂不能选。还需通过：……” → 回答附条款清单。

**链路 C（条款）**：问题属转专业/认定/免修等 → 不走核算 → 直接返回检索命中的原文条款（页码 + 行号 + 匹配度）。

**链路 D（档案与规划）**：用户问“查看我的档案”时走 `/profile-summary`；问“修读规划/选课建议”时走 `/study-plan`，服务端按已修课程、模块缺口与先修条件给出当前可修课程。档案删除/清空走 `/profile-command`，要求明确确认后才执行。

### 4.2 工作流节点与职责

工作流采用“先分流、再调用、后组织”的结构。模型节点只处理意图识别和受限文本组织；涉及个人课程记录、学分数量和先修资格的结果均由服务接口返回。主要节点如下。

| 节点 | 输入 | 处理内容 | 输出或后续节点 |
| --- | --- | --- | --- |
| 开始节点 | 用户问题、档案标识 | 接收会话参数；档案标识用于关联已修课程记录 | `question`、`profile_id` |
| 意图识别 | 用户问题 | 识别学分、先修、档案、规划或条款咨询；提取明确出现的课程代码 | 问题类型、课程代码 |
| 外部知识库检索 | 用户问题、问题类型 | 按问题类型检索培养方案或教务条款，并保留页码、表格行号 | 检索片段与引用信息 |
| 条件分支 | 问题类型 | 将问题分至学分核算、先修判定、档案规划或条款问答链路 | 对应 HTTP 节点或回答节点 |
| 学分核算 HTTP 节点 | `profile_id`、当轮课程代码 | 调用 `/audit`；服务端合并已保存记录，按模块计算缺口 | 结构化核算结果与摘要 |
| 先修判定 HTTP 节点 | `profile_id`、目标课程 | 调用 `/prereq`；执行先修表达式树求值 | `可以选` 或待补课程清单 |
| 档案与规划 HTTP 节点 | `profile_id` | 调用 `/profile-summary`、`/study-plan` 或 `/profile-command` | 已修课程、模块进度、建议课程 |
| 引用整理节点 | 检索结果、接口结果 | 将命中条款按来源、页码和行号整理为可核对清单 | 统一的引用文本 |
| 回答节点 | 结论、引用、问题类型 | 按不同问题类型使用对应格式输出，避免在先修结论中增加无关说明 | 面向用户的最终回答 |

其中，先修判定分支使用服务端返回的简短结论，不再经过模型扩写；学分核算分支则在保留数字结果的基础上，补充各模块缺口。对一般条款咨询，只使用检索内容，不触发档案写入或核算接口。

### 4.3 接口与档案数据约定

外部知识服务以 HTTP 接口对接 Dify。接口以 `profile_id` 作为档案主键，用户可以在开始节点填写学号，也可以使用自设匿名标识。课程记录只保存课程代码与通过状态，不保存姓名、联系方式和成绩单附件。

| 接口 | 请求中的主要字段 | 返回的主要字段 | 使用场景 |
| --- | --- | --- | --- |
| `POST /audit` | `profile_id`、`completed_courses` | 模块要求、已认定学分、模块缺口、剩余学分、未认定课程 | 查询毕业还差多少学分 |
| `POST /prereq` | `profile_id`、`course_code`、`completed_courses` | 是否满足、直接阻塞课程、解析状态、依据条款 | 查询某门课程能否选修 |
| `GET /profile-summary` | `profile_id` | 已修课程、各模块进度、档案更新时间 | 查看个人档案 |
| `GET /study-plan` | `profile_id` | 当前可修课程、待补先修、模块缺口 | 查询修读规划 |
| `POST /profile-command` | `profile_id`、`command`、`confirm` | 操作结果、更新后的课程数量 | 添加、删除或清空档案课程 |

课程写入采用“课程代码去重”的方式：同一课程重复提交不会累计学分；用户在单次提问中补充的课程，会与该档案已保存课程合并后再参与核算。清空和删除操作必须带确认字段，避免把普通问句误识别为写入指令。若课程代码不在当前培养方案中，接口会将其列入“未认定课程”，但不会计入任何模块。

**工作流变量流转。** 开始节点中的 `profile_id` 在整条链路中保持不变，`question` 只作为本次用户问题使用。意图识别节点输出 `intent` 和 `course_code`；条件分支依据 `intent` 选择服务接口；HTTP 节点将接口返回中的 `summary`、`eligible`、`missing_courses` 或模块明细传给回答节点。引用整理节点只接收检索结果，不读取或展示档案中的全部课程，避免在条款咨询中暴露与问题无关的个人修读信息。

**课程记录合并规则。** 当用户说“我已修 EE101、CS101、VE201”时，课程提取节点得到代码列表并提交给服务端。服务端先读取 `profile_id` 对应的历史记录，再与本轮代码合并、按课程代码去重，最后写回档案并执行核算。这样，同一用户在新对话中继续提问时仍可读取已有记录；如果用户只是在询问课程介绍、培养方案条款或其他与个人状态无关的问题，工作流不会发起写入操作。

**结果组织规则。** 学分问题的回答必须包含“剩余学分”与“模块缺口”；先修问题优先输出“可以选”或“暂不能选”，并只列出缺失的直接条件；档案问题输出已修课程数和模块进度；条款问题则给出检索条款及其页码、行号。回答节点不得自行改写 `eligible`、`remaining_credits` 等接口结论，也不得把检索不到的内容补写为通用建议。

**发布前检查。** 每次更新工作流时，先检查外部知识库地址、`campus-kb` 服务健康状态、SSRF 私网域名白名单和模型配置；随后导入 DSL，在 Dify 中发布新版本，并使用固定档案标识分别测试学分、先修、档案和条款四类问题。测试通过后再保留该版本作为可演示版本，避免工作流节点调整影响已有的核算结果。

### 4.4 关键实现

**(1) 表格解析器（`core/parser.py`，467 行）**

- 支持 Markdown 表格与 PDF（pdfplumber）两种来源，统一成 `Table(title, page, headers, rows)`。
- 表分类顺序经实测确定：**先判"先修表"（有先修列且有课程代码/名称）→ 再判"课程表"（有学分且有代码/名称）→ 最后判"模块表"**。顺序颠倒会导致无课程代码的课程表被误判为模块表（实测踩过，课程数变 0）。
- 先修文本解析采用"优先级解析"：`或` 低于 `且`；原子先匹配"N 学分"走学分门槛分支，否则剥离动词与限定词后按课程名查代码；**查不到就记入 `unresolved` 并告警，绝不伪造课程代码**。
- 两遍扫描：第一遍只读学分结构表拿到模块集合与总学分，第二遍解析课程表/先修表并把模块集合传入，解决"已完成专业核心课不少于 40 学分"里修饰词带偏模块名的问题。

**(2) 先修表达式树（`core/graph.py`）**

`PrereqExpr` 支持 `course / and / or / credits` 四类节点，附带形状校验（如 `credits` 必须有模块名与正学分）。求值语义：

- `and`：取阻塞项并集；
- `or`：任一满足即通过，全不满足时给出**阻塞项最少的分支**作为"最省力路径"；
- `credits`：读"该模块已修学分"，与学分核算共用同一份认定结果；
- 环检测在 visited 剪枝**之前**执行（否则环上叶子被静默跳过，测试抓出）。

**(3) 学分核算规则（`core/scoring.py`）**

| 规则 | 内容 |
| --- | --- |
| R1 | 只计 `passed=True` 的课程 |
| R2 | 培养方案外的课程不计入任何模块，记入"未认定"清单 |
| R3 | 学分以培养方案登记值为准；学生上报值与方案不一致时告警 |
| R4 | 模块超额部分**不冲抵**其他模块缺口 |
| R5 | 剩余学分 = 各模块缺口之和（**不等于**总学分 − 已修学分） |

R5 是最容易被误解的一条：核心课超修 4 学分不能让选修课的 8 学分缺口变成 4，否则学生按错误口径排课。评测集里专门有一条用例锁死这个差异。

**(4) 混合检索（`core/index.py` + `core/intent.py`）**

流程：结构化过滤先行（16 个算子，字段缺失一律不匹配）→ BM25Plus 与稠密通道分别打分 → min-max 归一 → weighted/RRF 融合 → 意图加权（同表类型 ×1.15）→ 证据门槛（两通道均为 0 的命中直接丢弃）→ 阈值截断。

两处经实测修正：

- **证据门槛**：Dify 默认 `score_threshold=0.0`，归一化后无关分块得分恰为 0，会被全部放行；因此额外要求"至少一个通道有原始分"。
- **意图加权**：同一门课同时出现在课程设置表与先修要求表，纯词法分几乎打平（"数据结构与算法几个学分"命中先修表）。按问题类型给目标表型加 1.15 倍权重后，Recall@1 由 0.833 升到 1.000。

**(5) Dify 应用层集成（`dify-workflow/build_chatflow.py`）**

工作流 DSL 由脚本生成，避免手写 YAML 时遗漏节点必填字段。集成过程中的关键工程问题包括：

1. **HTTP 节点响应体是字符串**，取不到 `body.summary`，渲染成字面量 → 服务端增加 `format=text` 直出 Markdown；
2. **外部知识库必须带 `external_retrieval_model`**，否则 `datasets.retrieval_model` 为 NULL，检索被静默跳过（日志 `Skipping dataset retrieval because retriever failed, error='NoneType' object has no attribute 'get'`）；
3. **开始节点不能声明 `query` 变量**（与 `sys.query` 冲突，服务 API 报 `query is required in input form`）；
4. **代码节点无外网** → 核算必须走 HTTP 节点，代码节点只做文本整理；
5. **SSRF 代理拦截内网** → 用官方 `SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=campus-kb` 与 compose 网络放行，不改 squid 模板；
6. **`sys.user_id` 随匿名会话变化** → 改为开始节点显式 `profile_id`，避免新对话丢失课程档案；
7. **模型会扩写选课结论** → 先修分支改为确定性 `format=brief`，最终回答不经过模型改写。

由于 Dify 官方引用列表仅在 LLM 节点消费检索上下文时生成，本项目使用代码节点显式渲染引用清单，并保留表行号。

**(6) 部署脚本（`deploy/`）**

部署脚本已处理两项 PowerShell 兼容性问题：其一，`ErrorActionPreference='Stop'` 会将原生命令写入 stderr 的构建进度视为错误，现改为仅在退出码非 0 时终止；其二，裸参数 `-d` 可能被 PowerShell 解释为函数参数，现改为以数组传递 `docker compose up -d` 参数。连续执行两次均正常结束。

### 4.5 知识库构建与索引过程

培养方案原始材料中既有连续文本，也有课程表、学分结构表和先修条件表。直接按固定长度切分文本，会把同一行课程的代码、名称和学分拆散，导致“汽车理论多少学分”与“汽车理论的先修是什么”难以区分。因此，知识库构建以表格行为基本单元，并保留表名、页码、行号和字段类型。

| 阶段 | 输入 | 处理方式 | 产物 |
| --- | --- | --- | --- |
| 文档读取 | Markdown 或 PDF 培养方案 | 提取标题、段落和表格；PDF 表格通过 pdfplumber 读取 | 原始文本块、表格对象 |
| 表格规范化 | 表头与表格行 | 统一课程代码、课程名称、学分、模块、先修字段的命名 | 结构化课程记录 |
| 表型识别 | 表格标题、列名和行内容 | 区分模块要求表、课程设置表、先修要求表和一般条款表 | 带表型标签的记录 |
| 引用定位 | 页码、行号、原文 | 对每条记录附加来源位置与原始文本片段 | 可核对证据单元 |
| 检索索引 | 证据单元 | 建立 BM25Plus 倒排索引；可选接入稠密向量通道 | 可按问题检索的索引 |
| 质量检查 | 课程记录与模块记录 | 检查重复代码、缺失学分、模块总分不一致和无法解析的先修文本 | 解析告警与检查报告 |

对于课程表，系统以课程代码作为优先键，以课程名称作为辅助匹配键。用户输入“汽车电子控制”时可以定位到 `VE205`；用户直接输入 `VE205` 时则不需要模糊匹配。对于课程名称相近、简称或别名，系统只将其作为检索关键词，不会直接写入个人档案，避免将相似课程错误认定为已修课程。

索引中同时保存“展示文本”和“计算字段”两类信息。展示文本用于在回答末尾列出培养方案原文；计算字段用于学分核算和先修表达式求值。两者分离后，修改回答样式、增加引用说明不会影响课程规则，更新课程规则也不需要重新设计对话模板。

### 4.6 三类核心业务的处理步骤

**学分核算。** 服务端先从档案中取出已通过课程，按培养方案课程表确认每门课程的所属模块与方案学分。随后分别累加通识教育、工程基础、专业核心、专业选修和实践环节的已认定学分，并与每个模块的最低要求比较。最终返回各模块缺口、未认定课程和总剩余学分。这个顺序保证了模块超修不会被错误地用于抵扣其他模块。

| 步骤 | 处理内容 | 结果 |
| --- | --- | --- |
| 1 | 读取档案与本轮补充课程，按代码去重 | 已修课程集合 |
| 2 | 查询课程表，确认课程是否在本培养方案内 | 已认定课程、未认定课程 |
| 3 | 按课程所属模块累加方案登记学分 | 各模块已获学分 |
| 4 | 用“模块要求 − 已获学分”计算缺口，最小值取 0 | 各模块缺口 |
| 5 | 汇总各模块缺口并生成摘要 | 剩余学分与可核对明细 |

**先修判定。** 用户问题中包含“能选吗”“先修条件”“修完后能否学习”等表达时，工作流优先寻找目标课程。服务端读取该课程的先修表达式，递归判断每个课程节点或学分门槛节点。对于“且”关系，所有子条件都需要满足；对于“或”关系，只要任意路径满足即可。若均不满足，则返回缺失项目最少的一条路径，使用户能够直接看到下一步需要修读什么。

**档案与修读规划。** 档案查看不重新计算每门课的成绩，而是展示已保存课程和最近一次核算得到的模块进度。修读规划以“尚未通过、先修条件已满足、属于有缺口模块”为筛选条件，优先列出当前可选且能填补学分缺口的课程。规划结果是建议顺序，不替代学校实际开课计划、容量限制或选课资格审核。

### 4.7 规则更新与版本管理

培养方案通常按年级或版本发布，同名课程的学分、模块归属和先修关系可能发生变化。系统将培养方案版本作为知识库配置的一部分；在导入新版本时，不直接覆盖已存在的解析结果，而是先生成新的结构化数据和索引，再完成对照检查。

| 更新环节 | 检查内容 | 处理要求 |
| --- | --- | --- |
| 文档入库 | 文档版本、适用年级、专业名称 | 建立独立版本标识，不覆盖旧版本 |
| 解析检查 | 课程数、模块数、总学分、未解析条目 | 与原方案表格逐项抽查 |
| 规则对照 | 学分、模块、先修条件变更 | 输出差异清单，供人工确认 |
| 检索评测 | 条款、课程、先修问题的命中情况 | 运行固定检索评测集 |
| 核算回归 | 模块缺口、超修、方案外课程 | 运行核算与先修测试 |
| 工作流发布 | 服务地址、知识库标识、模型配置 | 通过测试后导入并发布新版本 |

档案记录与培养方案版本需要同时保留。学生查询时应优先使用其入学年份对应的培养方案；在演示版本中，档案默认绑定当前样例方案。若后续接入多专业或多届学生，可在档案中增加专业代码和培养方案版本字段，并在开始节点中根据身份信息自动选择知识库与核算规则。

### 4.8 多专业扩展设计

现有样例以一个专业的培养方案为基础，但解析、检索与核算服务并不依赖具体课程名称。课程、模块、先修关系和条款均从培养方案数据中读取，因此接入新专业时主要新增数据与配置，而不是复制一套工作流代码。

| 扩展对象 | 当前实现 | 接入新专业时的处理 |
| --- | --- | --- |
| 培养方案 | 一个样例方案、一组课程与模块规则 | 新建方案版本，重新解析课程表、模块表和先修表 |
| 知识库索引 | 索引记录带表型、页码和行号 | 按专业和版本建立独立索引，检索时限定范围 |
| 档案数据 | `profile_id` 关联已修课程代码 | 增加专业代码、入学年份和方案版本字段 |
| 核算规则 | R1—R5 为通用规则 | 保持规则不变，读取目标方案的模块阈值 |
| Dify 工作流 | 意图识别、条件分支、HTTP 调用 | 在开始节点增加专业/方案参数，或由认证信息自动注入 |

多专业环境下，同一课程代码可能在不同方案中对应不同学分或模块。为避免档案被错误解释，查询接口必须先确定培养方案版本，再读取课程规则；不能仅凭课程名称在所有知识库中全局搜索。对于跨专业转入、课程替代或免修认定等特殊情形，可在课程记录中增加“认定来源”和“人工审核状态”，由教务人员确认后再参与学分核算。

服务层和工作流层保持松耦合：工作流负责收集问题与上下文，服务端根据专业配置返回核算结论。这样，在后续增加新的培养方案、院系条款或选课规则时，主要修改知识数据与接口配置，已有的对话分流、引用展示和错误处理逻辑可以继续复用。

接入一份新培养方案时，可按以下顺序实施：首先整理课程表、模块学分要求和先修条件表，确认文件中的版本号与适用对象；其次运行解析脚本，检查课程总数、模块总学分和无法识别的表格行；然后为该方案建立独立索引，并用课程代码、毕业学分、先修条件等问题进行检索抽查；完成数据检查后，再把方案版本写入服务配置，使核算接口能够按档案版本选择规则；最后在 Dify 中使用新方案的测试档案完成学分、先修、档案和条款四类回归测试。

为便于维护，规则变更应保留变更记录，至少包含调整日期、原始条款位置、修改内容、影响课程和验证结果。例如，某门课程从专业核心课调整为专业选修课时，需要同时更新课程模块、模块缺口计算和检索索引，并对已保存档案重新执行核算。将这些步骤固化后，培养方案更新不再依赖人工逐页检查，也能为后续扩展多个专业提供统一流程。

### 4.9 档案状态与课程认定流程

个人档案的设计目标是让用户能够在多次对话中逐步补充已修课程，同时不把自然语言中的模糊表述直接当作正式学业记录。为此，系统将“用户提及课程”“课程写入档案”和“课程计入学分”拆分为三个阶段：提取阶段只得到候选课程代码；写入阶段按档案标识保存确认后的代码；核算阶段再按当前培养方案确认课程归属和学分。

| 状态 | 进入条件 | 系统保存内容 | 是否参与核算 |
| --- | --- | --- | --- |
| 候选课程 | 用户问题中出现可识别课程代码或全称 | 本轮请求中的候选代码 | 否 |
| 已保存课程 | 用户明确表示“已修”“已通过”，或通过档案指令添加 | `profile_id`、课程代码、通过状态、更新时间 | 是，等待方案匹配 |
| 已认定课程 | 课程代码存在于目标培养方案且状态为通过 | 课程所属模块与方案学分 | 是 |
| 未认定课程 | 课程不在目标方案、代码无效或方案版本不匹配 | 课程代码与未认定原因 | 否 |
| 已移除课程 | 用户确认删除或清空档案 | 操作结果与更新时间 | 否 |

当用户只问“汽车电子控制的先修要求是什么”时，系统不会因为问题中出现课程名称就把 `VE205` 写入档案；只有用户明确表达已修、添加或更新课程时，才会调用档案写入接口。这样可以避免普通咨询改变个人数据。对于“我修过汽车电子”这类名称不完整的输入，系统可将其作为检索词返回可能课程，但不自动映射为某个课程代码，需由用户选择或补充完整名称后再写入。

课程认定还需要考虑培养方案版本。如果学生档案使用的是较早版本，而当前知识库默认版本发生了变化，服务端应优先读取档案绑定的版本；没有绑定版本的演示档案才使用当前默认方案。该机制可以避免同一门课程在不同年级、不同专业中学分不同而造成的误算。实际部署中可进一步接入统一身份认证和教务成绩数据，使“已通过”状态由系统同步而非用户手动填写。

### 4.10 异常处理与运行保障

培养方案问答的错误通常不是单一接口异常，还包括课程名称不完整、课程代码不存在、培养方案未覆盖、检索无命中和档案状态不一致等情况。系统在服务端保留解析状态，并在工作流中根据状态选择相应提示，避免将不确定信息包装成确定结论。

| 情况 | 服务端处理 | 对话侧反馈 |
| --- | --- | --- |
| 用户未给出目标课程 | 不执行先修求值，返回 `resolved=false` | 提示补充课程代码或课程全称 |
| 课程代码不在培养方案中 | 不计入模块，记录为未认定课程 | 说明该课程暂未被当前方案识别 |
| 先修文本无法完整解析 | 保留未解析片段，不生成猜测性的课程依赖 | 提示以培养方案原文或教务系统为准 |
| 检索没有可靠命中 | 低于证据门槛的片段直接丢弃 | 返回“未检索到相关条款”，不拼接相似内容 |
| 同一课程重复写入 | 按课程代码去重后保存 | 返回当前档案的有效课程数量 |
| 删除或清空档案 | 必须同时提供明确命令和确认字段 | 未确认时只提示操作方法，不改变档案 |
| 外部知识服务不可达 | 健康检查返回非正常状态，HTTP 节点保留错误信息 | 提示稍后重试，不输出旧会话中的核算结论 |

服务使用 Docker Compose 与 Dify 部署在同一网络中。Dify 访问 `campus-kb` 时通过 `SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=campus-kb` 放行服务名，而不对整个私网网段开放访问权限。服务提供 `/health` 用于检查容器是否可用；导入工作流前还会检查接口地址、环境变量和外部知识库登记状态。

在测试阶段，核算、先修、检索和档案接口均使用固定样例做回归验证。发布新的培养方案或修改规则后，应先执行解析与评测脚本，再导入新的工作流版本；这样可以将“规则变化”与“对话模板变化”分别检查，减少上线后才发现学分计算错误的风险。

| 用途 | 工具类型 | 是否影响结论 |
| --- | --- | --- |

核算结果、评测指标和测试用例均由代码生成，可独立复现。

### 5.4 已知局限

1. 真实语料仅 2 份教学大纲（1 张 PNG、1 份旧版 `.doc`），且均为**课程级**文档；PNG 需 OCR、`.doc` 需先另存，二者不在 MVP 范围，故真实数据目前只用于人工对照，未进入自动链路。
2. 稠密通道默认关闭（保证离线可跑）；启用后需 GPU 或较慢的 CPU 推理。
3. 不处理绩点换算、重修覆盖、证书抵免等教务细则。
4. 评测集由团队标注，存在标注者偏差；已公开用例文件供第三方复算。
5. 意图识别为关键词词典，对非常规表述（如"这门课我够格吗"）可能落到条款分支。
6. 课程档案目前以用户自设标识绑定，尚未对接统一身份认证或教务成绩单；生产部署需增加认证、权限与审计。

## 六、创新性与开放价值

### 6.1 创新点

1. **可核算问答**：检索负责定位依据，确定性代码负责计算结论，并输出可核对的行级引用。
2. **表格级结构化而非切片级检索**：以"表行"为最小单元并保留页码/表行号，使引用可核对到原文位置；检索结果天然带结构化元数据，可做模块/课程/表型过滤。
3. **意图加权消歧**：同一门课在多张表中出现时，用问题类型（先修/学分/学期/模块）对表型加权，使 Recall@1 从 0.833 提高到 1.000。
4. **应用层集成路径**：通过外部知识库契约、HTTP 节点、代码节点和 compose 覆盖文件接入自研服务，全程未修改 Dify 源码；相关配置与问题处理记录见 `docs/05`。

### 7.2 数据权利与隐私

- 仓库**不含**任何真实培养方案、真实教学大纲、学生成绩与个人信息；真实语料仅在本地演示，`data/real/` 已被 git 忽略。

### 7.3 AI 输出与内容安全

- 数字类输出与先修结论**不经过模型**，避免幻觉与算错；
- 千问只接收完成意图识别、课程提取和受限表述所需上下文，不承担课程档案写入、学分计算或选课判定；
- 检索无命中时明确返回"未检索到相关条款"，不做兜底编造；
- 先修判定无法解析时返回 `resolved=false` 并提示补充信息，不猜测课程代码。

### 7.4 IP 与公开边界

- 未复制 Dify 源码；仅调用其公开接口与扩展点；
- 文档与代码均为原创；第三方资源在附录逐项登记义务与合规状态；
- 公平性：报告、视频、PPT 不含校名、校徽、指导教师信息。

## 八、总结与展望

本项目将培养方案问答拆分为条款检索、规则计算和结果引用三个环节：检索负责定位依据，代码负责计算结论，引用保留到表行位置。在不修改 Dify 源码的前提下，使用官方扩展点完成外部知识库、工作流编排和答案渲染的集成，并提供自动化测试与评测脚本。

后续三个方向：

1. **语料工程**：接入 OCR 与版式还原，把 PNG/扫描版教学大纲纳入链路；支持 `.doc` 批量转换。
2. **AI 能力增强**：继续评测千问意图识别与查询改写的覆盖率，保留规则兜底；稠密通道接入 bge-m3 与重排模型。
3. **生态复用**：把"外部知识库契约实现 + 表格解析器"抽成通用模板，服务更多校园文档场景（实验守则、竞赛规程、科研报销规定）。
