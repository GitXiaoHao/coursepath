## 1. 第 1 阶段：路径决策（10/19）

| 维度 | 路径 A：插件提交市场 | 路径 C：工作流 + 自研外部组件 |
|---|---|---|
| 作品形态 | `.difypkg` + 仓库 | Chatflow DSL + 自研 Docker 服务 +（可选）插件包 |
| AI 与开源融合 | 中：插件薄，AI 能力靠宿主 | 高：检索/重排/结构化抽取均为自研 AI 组件，全栈开源选型 |
| 实质技术贡献 | **弱到中**：无自有后端时只能包别人的 API，正是审核易判"机械封装"、赛题易判"仅调用通用接口"的形态 | **强**：结构化解析 + 图算法核算 + 混合检索，全在 Dify 之外 |
| 开发成本 | 低（2–3 人日） | 中高（6 人日 + 服务 2 人日） |
| 合规风险 | 中：非机械性审核、PR 合入时间不可控 | 低：以仓库 + 服务交付，不依赖第三方合入 |
| 可验证性 | 强（安装/打包/校验器退出码） | 强（接口测试 + 检索指标 + 端到端 trace） |
| 与方向匹配 | 方向三 | 方向一（并用插件产物佐证方向三） |
| 12 天可行性 | 高 | 中（需严格裁剪） |

**推荐排序：C > A**，理由：
1. **A 无法独立成立**——没有自有后端的工具插件只能包第三方 API，既最易被市场审核判为缺乏独特性，也是赛题评分中"仅调用通用接口"的典型形态。A 必须以 C 的自研服务为底座。
2. **完成度占 25 分且同分优先**，3–5 分钟视频需要完整可跑链路；A 能演示的只是一个安装界面。
3. **PR 合入时间不受团队控制**，把外部 review 队列当门禁 = 把晋级交给别人。⇒ 插件降为加分项：先做到"本地可安装 + 校验器通过 + 仓库开源"，能合则锦上添花。

**路径 B（Fork + 上游 PR 二次开发）：不可行，放弃。** 团队无法维护 rebase；上游迭代过快（当前 1.17.1，2026-09-10，伴随 Weaviate 强制分阶段升级）；交付不可维护产物反在"开放成果复用价值/维护计划"扣分。

### 1.1 路径 C 的具体口径

- **作品名**：`课径 · 可核算的培养方案问答`（不出现学校名，≤20 字）
- **场景**：学生自助回答"还差哪些学分 / 这门课先修满不满足 / 转专业后哪些课能抵"——现状是翻 PDF + 问辅导员，答案分散、易错、无法追溯依据。
- **AI 必要性**：表格、跨页条款、自然语言先修描述必须靠模型做结构化抽取与查询理解；答案需引用归因。
- **可演示 MVP**：1 个专业、约 200 份文档、1 条主链路 → "大二下想选《X》，先修满足吗？毕业还差多少学分？" → 结论 + 逐条引用（文档/页/表格行）+ 计算过程。
- **开源产出**：`campus-kb` 服务仓库（Apache-2.0）+ `course-path.chatflow.yml` +（加分）`course-audit` 工具插件 `.difypkg` + 评测集与脚本。
- **市场空白论证方法（客观化）**：在 marketplace 与 `dify-plugins` 仓库按固定关键词表（`knowledge base` / `retrieval` / `rag` / `education` / `campus` / `course` / `knowledge connector`）检索，记录命中插件名与数量作附录证据；结论表述为"**面向中文教务文档结构化检索与学分核算的服务型插件未见同构实现**"，而非"完全没有"。

**门禁 G1（一句话检验，须书面通过）**
> "我们做的什么事，是单纯在工作流里拖拽现成节点、或直接调用通用模型 API 做不到的？"
> 答：**"先修链是否满足""还差多少学分"是确定性计算，需要课程依赖图与规则引擎；Dify 分段检索与 LLM 提示词无法保证 100% 一致的计算结果，也无法把答案归因到表格某一行。**

### 2.2 Dify 内外边界表

| 能力 | Dify 内（编排层） | Dify 外（自研，实质贡献） |
|---|---|---|
| 意图/参数抽取 | LLM 节点 + 团队提示词 | — |
| 查询改写、指代消解 | LLM 节点 + 提示词 | 改写策略的可选服务端实现 |
| **文档解析与结构化** | ❌ 内置分段破坏表格语义 | ✅ `core/parser.py` |
| **课程图与先修判定** | ❌ 无法确定性图遍历 | ✅ `core/graph.py` |
| **混合检索/融合/元数据过滤** | 部分（内置检索） | ✅ `core/index.py`（接受 `metadata_condition`） |
| **学分核算** | ❌ | ✅ `core/scoring.py`（规则 DSL + 单测） |
| 答案生成与引用呈现 | LLM 节点 + 输出模板 | — |
| 拒答/一致性校验 | 代码节点（纯规则，无网络） | `/audit` 的 `explain[]` 作事实源 |
| 部署运维 | docker compose（官方） | 自有 `Dockerfile` / compose |

> 记录：**代码节点（dify-sandbox）默认无外网**，所有外部调用必须走 **HTTP 请求节点**。

### 2.3 接口定义（可脱离 Dify 独立测试）

**① 外部知识库契约**（严格对齐官方规范，否则接不上）
`POST {endpoint}/retrieval`，`Authorization: Bearer {API_KEY}`
- 请求：`knowledge_id`、`query`、`retrieval_setting{top_k, score_threshold}`（必填）、`metadata_condition{logical_operator, conditions[]}`（可选，需支持 `and/or` 与 `contains/is/in/>/</before` 等）
- 响应：HTTP 200 + `{"records":[{"content","score","title","metadata":{}}]}`
- **硬性陷阱**：`metadata` 必须为对象，`null` 会让 Dify 检索管线报错；缺 `content`/`score` 会被静默降权；无结果返回 `{"records": []}` 而非 404
- 错误：非 200 会向用户抛错；建议 `{"error_code":1001/1002/2001,"error_msg":...}`

**② 核算**：`POST /audit` → `{plan_id, target:{major,module}, completed:[{code,credits,grade}]}` → `{total_credits, earned, remaining, gaps:[{module,need,missing}], explain:[{rule,evidence}], version}`

**③ 先修**：`POST /prereq` → `{course_code, completed:[]}` → `{ok, chain:[], blockers:[{course,satisfied_by}], evidence:[]}`

**④** `GET /health`（索引版本/文档数/模型版本）、`GET /openapi.json`

**独立测试口径**：pytest 覆盖契约字段、`metadata:null` 防护、空结果、鉴权失败、超时降级；`pytest -q` 全绿即证明"不依赖 Dify 界面"。

### 2.4 插件方案（路径 A 分支）

- **类型**：`tool`，挂 3 个 tool（`search_course` / `check_prerequisites` / `audit_credits`）；**不选** datasource（不抓网页）、**不选** extension（方向相反）。
- **manifest 策略**：**不手写**，`dify plugin init` 生成骨架后仅改：`author`（**不得含 `langgenius` 或 `dify`**）、`name`（≥3 字符、`-` 连接）、`icon`（`_assets/icon.svg` 必须自定义）、`resource.memory`、`meta.runner`（python 3.12 + entrypoint）、`privacy: PRIVACY.md`、`tags`。
- **依赖**：`dify-plugin` 按模板生成（现行要求 **>= 0.9.0**，PyPI 实测 0.10.2，均要求 **python>=3.12**）；业务依赖尽量为零（只用 `httpx`），降低安装失败与 OSV 命中。
- **风险等级**：勾 **Low risk**（只调固定文档化 HTTPS API，无代码执行/文件/SQL/任意 URL）。
