**评分权重**：问题与场景 15 / 创新性 20 / AI 与开源融合 20 / **实现完成度 25** / 开放成果 15 / 材料 5。

**一票否决**：抄袭、IP 侵权、许可证重大违规、数据安全/伦理。

## B. 工程边界（团队能力圈）

| # | 边界 | 说明 |
|---|---|---|
| B1 | **不修改、不 fork `langgenius/dify` 源码** | 团队无人具备改核心源码能力；fork 后无法维护 rebase（上游 1.17.1，2026-09-10 发布，伴随 Weaviate 强制分阶段升级） |
| B2 | 允许的交付形态 | `.difypkg` 插件 / 工作流 DSL / 自研外部 HTTP 服务 / 外部知识库服务 / 文档与数据 |
| B3 | **部署配置 ≠ 源码 patch** | `docker/ssrf_proxy/squid.conf.template` 加白、`.env`、compose 端口映射均属部署配置，不触碰源码。该区分须在报告"七、合规"中**主动声明**，避免被误判 |
| B4 | 平台既有硬限制（不可绕过，只能适配） | ①代码节点 `dify-sandbox` **默认无外网** → 外部调用必须走 **HTTP 请求节点**；②Dify 出站经 **SSRF 代理**，域名不在白名单会被拦截 → 须加白并重启代理容器；③**外部知识库是平台原生功能**（登记 Endpoint + `knowledge_id` + API Key），**不是插件类型**；④插件类型仅 6 种：tool / model / agent_strategy / extension(Endpoint，外部调进来) / datasource(外部文档导入) / trigger |
| B5 | 许可证限制 | Dify 为**修改版 Apache-2.0**：①**多租户 SaaS 需商业许可**（一租户=一 workspace）→ 只做**单租户自托管**；②**不得移除/修改前端 LOGO 与版权信息**（`web/` 目录或 web 镜像） |
| B6 | 不得引入 AGPL 依赖 | 已选 `pdfplumber`(MIT) 规避 PyMuPDF(AGPL-3.0)、Ghostscript(AGPL) |

**"必须改源码才能实现"的设想 → 一律标注不可行并放弃，不得包装成"配置就能做到"。**

## E. 明确的"不可行"清单（放弃，不再讨论）

1. **Fork Dify + 向上游提 PR 二次开发** —— 无法维护 rebase，上游迭代过快，交付不可维护产物。
2. **把"外部知识库"做成一种插件类型** —— 不存在该类型；外部知识库是平台原生功能。
3. **代码节点内直接调用外部服务** —— sandbox 默认无外网。
4. **多租户 SaaS 形态参赛** —— 需 Dify 商业许可。
5. **移除/替换 Dify 前端 LOGO 做作品品牌** —— 许可证禁止。
