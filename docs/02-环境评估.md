# 02 · 本机环境评估与部署方案决策

> 状态：✅ 已完成 · 2026-10-18 实测
> 结论先行：**本机可以承担开发，但"在笔记本上跑整套 Dify 做现场演示"不是最优选择**；推荐"本机开发 + 轻量云主机部署演示"双轨。

## 2. 可行性判定

| 场景 | 判定 | 说明 |
|---|---|---|
| 开发 `campus-kb` 服务（Python + FastAPI + pytest） | ✅ **完全可行** | 内存 <1 GB；CPU 足够；M: 盘空间充裕 |

## 3. 三个部署方案对比

| 方案 | 组成 | 内存/成本 | 外网可达性 | 风险 | 适用 |
|---|---|---|---|---|---|
| **① 本机 Docker Desktop + WSL2** | 本机跑 Dify 全栈 + `campus-kb` 同机 | 吃 6–8 GB 内存；免费 | Dify 与自研服务同 compose 网络 → **必须**给 SSRF 代理加白内网域名 | 安装需管理员权限 + 重启；内存紧张；换页导致录屏掉帧 | 开发调试、离线演示备份 |
| **② 轻量云主机（推荐）+ 本机开发** | 云主机 2C4G/4C8G 跑 Dify + `campus-kb`，域名 + HTTPS；本机只写代码与录屏 | 约 ¥60–150/月；内存独立 | 公网 HTTPS 域名，**仍需**在 squid `allowed_domains` 加该域名 | 需备案/域名（用 IP + 自签或用支持 HTTPS 的临时域名可绕过备案）；持续费用 | **正式演示与视频录制** |
| **③ Dify Cloud + 隧道暴露本地服务** | cloud.dify.ai + cloudflared/ngrok 暴露 `campus-kb` | 免费额度 | 隧道域名需加入云端白名单（不可控） | 云端 SSRF 白名单操作权不在我们手上；免费隧道不稳定；演示依赖第三方 | 不推荐作主线 |

## 4. 决策

- **D1 开发期**：本机直接跑 `campus-kb`（Python 3.11 + venv），**不装 Dify** 也能完成 80% 工作（接口契约、检索、图算法、核算、评测全部可用 pytest/curl 验证）。这与"C1：分数押在 Dify 之外"的评审偏好一致。
- **D2 集成期（10/21 spike）**：优先申请/购买一台**轻量云主机**（2C4G 起）跑 Dify 1.17.1 compose；本机通过公网访问其 Web 做编排。若拿不到，退方案 ①。
- **D3 演示与录屏**：在方案 ② 上录制，**并**在方案 ①（若已装好）留一份离线备份。视频提前录完本地留存，不依赖现场网络。
- **D4 embedding**：**主用 OpenAI 兼容的云端 embedding API**（省内存、与 Dify 内置知识库基线可用同一模型，保证对比公平）；**备用** 本地 CPU `bge-small-zh-v1.5`（约 95 MB，onnxruntime）。不使用 bge-m3 本地推理。
- **D5 插件打包**：补装 **Python 3.12**（或使用 daemon 容器），避免 `dify_plugin` 版本要求不满足。

## 6. 已知坑（提前规避）

1. **Docker 数据盘默认在 C:**，C: 仅剩 24 GB → 装完立刻改盘到 M:，否则构建镜像阶段就满盘。
2. **SSRF 代理**：无论方案 ①②，自研服务域名（内网名或公网域名）都必须加入 `docker/ssrf_proxy/squid.conf.template` 的 `allowed_domains` 并重启 `ssrf_proxy` 容器，否则外部知识库/HTTP 节点一律被拦。这是**部署配置**，不是源码修改（见 `00-约束清单.md` §B3）。
3. **代码节点无外网**：工作流里任何对外调用必须用 **HTTP 请求节点**，不要在代码节点里写 `requests`。
4. **家庭版权限**：Docker Desktop 安装需管理员；若被策略限制，直接切换方案 ②（云主机），不要在这上面耗时间。

## 7. 对原计划的唯一调整

原计划 10/21 的"环境 spike"增加前置条件：**Docker 与云主机的准备提前到 10/20**，spike 当天只做"登记外部知识库 → SSRF 放行 → 拉回 1 条 records"的验证。整体 12 天日历不变。

## 8. 阶段二 spike 实测记录（2026-10-18 12:30 起）

团队已安装 Docker Desktop 4.94（Docker Engine 29.8.2、Compose v5.5.1、WSL2 后端，分配内存 **15.4 GB**、16 vCPU）。以下是本次实测新发现，**推翻第 1 节的上表中的三条旧判断**：

| 项 | 旧判断 | 实测新结论 |
|---|---|---|
| Docker | 未安装 | ✅ 已装并可用；`docker.exe` 不在 PATH，需用全路径或 `deploy/bootstrap.ps1` 自动补 PATH |
| Docker 数据盘 | 必须迁到 M: | ⚠️ 暂未迁：C: 剩 18.9 GB，Dify 全套镜像约 4–5 GB，**够用**；若后续加模型权重再迁移 |
| Python 3.15 | — | ❌ **不可用于插件**：`pyyaml` 无 cp315 轮子，源码编译又要 MSVC 14；改用 python-build-standalone 的 **3.12.15** 放在 `.tools/python`（无需管理员、不污染系统） |

### 8.1 网络阻塞与规避（关键）

- `registry-1.docker.io` / `auth.docker.io` **直连基本不可用**（TCP 443 探测失败，`hello-world` 拉取耗时数分钟）。
- 已可达的镜像加速器：`docker.m.daocloud.io`、`docker.1panel.live`、`hub.rat.dev`、`docker.nju.edu.cn`。
- 已写入 `C:\Users\<user>\.docker\daemon.json` 的 `registry-mirrors` 并 `docker desktop restart`，之后 `redis:6-alpine` 等镜像秒级拉完。
  ⇒ **换机器/重装系统后第一件事就是配镜像加速**，否则评分演示环境会卡在拉镜像。

### 8.2 SSRF 放行有新解（不必改 squid 模板）

旧坑第 2 条说"必须改 `squid.conf.template` 的 `allowed_domains`"。实测 **`ssrf_proxy` 官方 entrypoint 已支持两个环境变量**，在 `docker/.env` 里设置即可，**完全不用碰模板**：

```
SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=campus-kb        # 按域名放行（本项目用这个）
SSRF_PROXY_ALLOW_PRIVATE_IPS=172.18.0.5           # 或按 IP 放行
```

entrypoint 会把它们写成 `dify_allow_private.conf` 中的 `http_access allow client_localnet ...`，**排在 `deny to_private_networks` 之前**，因此内网服务可达。`deploy/bootstrap.ps1` 已自动写入该变量。

### 8.3 部署编排方式

不改 Dify 源码、也不改官方 compose 文件：用 **compose 覆盖文件**（`deploy/dify.override.yaml`）把自研 `campus-kb` 服务并入同一个 compose 工程，加入 `ssrf_proxy_network`，使 Dify 能用 `http://campus-kb:8080` 访问它。`deploy/bootstrap.ps1` 负责克隆 `docker/` 目录、生成 `.env`、生成 `CAMPUS_KB_API_KEY`、复制覆盖文件并拉起。

### 8.4 真实数据现状（阻塞项）

`campus-kb/data/real/` 目前只有两份**课程层面**文档：

- `实验室安全教育教学大纲.png`（图片，2.78 MB，内容是《化学实验室安全教育》教学大纲，含课程编号 007102、学分 0.5）
- `研究生课程教学大纲[矩阵论].doc`（Word 97 二进制，156 KB）

**缺的是专业层面的《××专业培养方案》**——即包含「学分结构表 / 课程设置表 / 先修要求表」的那份文档。核算引擎（`/audit`、`/prereq`）的输入正是这三张表，没有它就无法跑真实数据。另：`.doc` 为旧二进制格式，Word COM 在本机打开该文件报 `NullReferenceException`（其他文档 `Documents.Add` 正常），建议另存为 `.docx` 或 `.pdf`。
