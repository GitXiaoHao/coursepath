# 05 · Dify 应用层集成说明（实现记录）

> 本文件记录「课径」在 **Dify 1.17.1 应用层**的落地方式，以及集成过程中被 Dify 行为
> 绊住并解决的具体问题。全部结论来自本机实测（2026-10-18），不修改 Dify 源码、
> 不修改官方 `docker-compose.yaml`。

## 1. 落地形态

```
Dify Chatflow（应用层，DSL 导入生成）
  ┌──────────┐   ┌────────────────────┐   ┌──────────────┐   ┌──────────┐
  │  start   │──►│ knowledge-retrieval│──►│ code(整理条款)│──►│ if-else  │
  └──────────┘   └────────────────────┘   └──────────────┘   └────┬─────┘
        │                 │ 外部知识库契约                         │
        │                 ▼                                        ├─ true  ─► HTTP /prereq ─► answer（先修）
        │        http://campus-kb:8080/retrieval                  ├─ clause ─► answer（条款摘录）
        │                                                        └─ false ─► HTTP /audit  ─► answer（学分）
        └─ 输入：completed（已修课程代码，逗号分隔）

campus-kb（自研 FastAPI 服务，Docker 容器，同一 compose 项目）
  POST /retrieval   外部知识库检索契约（Dify 调用）
  POST /audit       学分缺口核算（规则编号 R1–R5）
  POST /prereq      先修链判定（and / or / credits 三类表达式）
  GET  /health      健康检查（含语料规模、方案版本）
```

编排方式：`deploy/dify.override.yaml` 作为 `docker-compose.override.yaml` 与官方
compose 合并，**官方文件保持原样**；`campus-kb` 同时接入 `default` 与
`ssrf_proxy_network`，Dify 的检索器与 HTTP 节点都经 SSRF 代理出站。

## 2. 为什么服务端要支持 `format=text`

Dify 的 HTTP 请求节点把响应体存成**字符串**（`status_code / body / headers / files`），
`body` 不是字典。因此在 answer 节点里写 `{{#audit.body.summary#}}` 取不到子字段，
渲染出来是字面量 `audit.body.summary`（实测）。

三条路可选：

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| 代码节点解析 body 再取字段 | 多一跳、依赖 sandbox | 可用但更重 |
| 服务端返回 `text/plain` Markdown | 服务端多一个分支 | **采用** |
| answer 直接渲染整个 JSON | 用户看不懂 | 否决 |

实现：`/audit`、`/prereq` 的请求体加 `format: "json" | "text"`，`text` 时返回
`PlainTextResponse(summary())`；DSL 里 answer 节点写 `{{#audit.body#}}`。摘要文本本身
有 pytest 断言，不会为了"能显示"牺牲可测性。

## 3. 集成踩坑清单（现象 → 根因 → 解法）

### 3.1 外部知识库检索被静默跳过

- **现象**：工作流里知识检索节点返回 `result: []`，问答没有报错。
- **日志**：`WARNING [dataset_retrieval.py:1277] Skipping dataset retrieval because
  retriever failed, dataset_id=…, error_type=AttributeError, error='NoneType' object has no attribute 'get'`
- **根因**：`datasets.retrieval_model` 为 `NULL`。通过
  `POST /console/api/datasets/external` 建外部知识库时若不带
  `external_retrieval_model`，Dify 不会补默认值，检索线程读 `retrieval_model.get(...)` 直接炸。
- **解法**：建库时就带 `external_retrieval_model`：
  `{"top_k": 4, "score_threshold": 0.0, "score_threshold_enabled": false}`。
  已建坏的库用 `PATCH /console/api/datasets/<id>` 修，且**必须同时提供
  `external_knowledge_id` 与 `external_knowledge_api_id`**，否则 400：
  `ValueError: External knowledge id is required.`

### 3.2 开始节点不能声明 `query` 变量

- **现象**：服务 API 调用报 `ValueError: query is required in input form`。
- **根因**：Chatflow 的用户问题由系统变量 `sys.query` 承载；开始节点再声明同名变量
  会让 API 把 `query` 当成必填 inputs。
- **解法**：开始节点只放业务输入（`completed`），检索节点用 `["sys","query"]`。

### 3.3 `retriever_resources` 为空

- **现象**：`/v1/chat-messages` 返回的 `metadata.retriever_resources = []`，前端不显示引用。
- **根因**：Dify 只在 **LLM 节点消费检索上下文**时才构建官方的引用列表
  （`graphon/nodes/llm/node.py` 构造 `retriever_resources`）。本项目回答由确定性代码
  给出，没有 LLM 节点，因此官方引用机制不触发。
- **解法**：用**代码节点**把检索命中的 `kb.result` 渲染成"相关条款（检索命中，可逐条核对）"
  清单，每条带文档名、**页码、表行号、匹配度**，直接拼进 answer。这比官方引用更可核验
  （官方引用只有文档名与分数，没有表格行号）。

### 3.4 代码节点没有外网

- `dify-sandbox` 内的代码节点无法访问 `campus-kb`，所有跨服务调用必须走
  **HTTP 请求节点**；代码节点只承担纯文本整理（本项目的条款清单）。

### 3.5 SSRF 代理拦截内网服务

- Dify 出站经 Squid 代理。放行 `campus-kb` **不需要改 `squid.conf.template`**：官方
  `ssrf_proxy/docker-entrypoint.sh` 支持环境变量
  `SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=campus-kb`，会生成 `dify_allow_private.conf`
  且 `http_access allow client_localnet` 排在内网拒绝规则之前。

### 3.6 DSL 版本与导入结果

- 导入接口返回 `status: "completed-with-warnings"`，`current_dsl_version: 0.7.0`、
  `imported_dsl_version: 0.3.0`。门禁脚本按 `status.startswith("completed")` 判定，
  并把 warning 打印出来而不是当作失败。

### 3.7 `local_sandbox` 无限重启（官方 compose 与镜像参数不一致）

- **日志**：`flag provided but not defined: -require-auth-token`
- **解法**：覆盖文件里把 `local_sandbox` 的 command 改为
  `["shellctl","serve","--listen","0.0.0.0:5004"]`，不修改官方文件。

## 4. 复现步骤

```powershell
# 1) 起 Dify + campus-kb（幂等）
.\deploy\bootstrap.ps1

# 2) 生成 DSL → 导入 → 发布 → 冒烟（三路问题各一问）
campus-kb\.venv\Scripts\python.exe dify-workflow\build_chatflow.py --import
```

产物 `dify-workflow/course-audit.chatflow.yml` 即提交给评审的工作流 DSL（不含密钥，
`api_key` 由脚本从 `deploy/dify/docker/.env` 注入生成，**提交版需替换为占位符**）。
